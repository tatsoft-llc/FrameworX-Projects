# Glossary: workspace controlled vocabulary

Canonical terms for this delivery workspace, applied across every project's docs, specs, and skills. When
these words appear in a Requirements doc, a ChangeLog, a Decision note, or a skill, they mean what this table
says, nothing looser.

**This doc layers on top of the FrameworX platform model; it does not redefine it.** The product injects its
own definitions on connect (Solution, UNS, the Object Model's roots, the Four Pillars, Tags, UserTypes). Where
a term below is a platform term, the definition here is the platform's, re-stated only enough to fix how *this
workspace* uses it. If the two ever diverge, the product wins and this file is wrong.

| Term | Definition | Notes / relationship |
|---|---|---|
| **Project** | The complete automation engagement for one site / skid / line, its requirements, solution(s), and deliverables together. Physically, one folder under `Sites/<Name>/`. | The whole job, **not** the `.dbsln`. A Project *contains* one or more Solutions plus its Specifications, Documentation, Decisions, and ChangeLog. The workspace's top-level unit of work. |
| **Solution** | The specific FrameworX platform artifact, a `.dbsln` (plus its runtime artifacts) that Designer configures and Runtime executes. Lives in the Project's `Solutions/` folder. | **Platform term, the product defines it.** The product calls a Solution "a self-contained project *database*"; there, "project" means the database, not the engagement. So in this workspace: **Project = the engagement folder, Solution = the `.dbsln` inside it.** Most Projects have exactly one Solution. |
| **Application** | A *functional deliverable* the Project/Solution produces, e.g. the operator SCADA application, a reporting application, a dashboard. Loosely, an everyday synonym for Solution or Project. | Prefer the precise word: **Project** for the engagement, **Solution** for the `.dbsln`. Reach for "Application" mainly when naming *what the solution does for the customer* ("the pump-station SCADA application"). |
| **Specification** | A design input under a Project's `Specifications/`: the Requirements doc and the IO Register that drive the build. | "What it must do" + "what's wired." Source of truth for done; the Commissioning Record checks against it. |
| **IO Register** | The point list mapping every physical signal (Tag ID, type, address, range, alarm limits) to its **Target UNS Tag**. Lives at `Specifications/IO-Register.md`. | The bridge from field hardware to the UNS. UNS authoring reads it to create tags / UserTypes / device channels; commissioning reads it to know what to loop-check. |
| **UNS (Unified Namespace)** | The platform's hierarchical tag layer, the data foundation; the `Tag.*` namespace. | **Platform term.** Tag paths here follow `KnowledgeBase/Conventions/UNS-Naming.md` (`<Area>/<Equipment>/<Signal>`, PascalCase). Built-in namespaces (Device, Alarm, Historian, …) are *peers* of the UNS, not part of it. |
| **Tag** | An addressable runtime value in the UNS (`Tag.<path>`). A live value carries quality and a timestamp, not just a number. | **Platform term.** "Read it back" during commissioning means confirm value **+ Good quality + a recent timestamp**: a plausible number with Bad/stale quality is not a pass. Quality codes: Good 192 / Uncertain 64 / Bad 0. |
| **UserType (UDT)** | A reusable structured type with members; its instances are tags whose members are individually addressable. | **Platform term.** "UserType" and "UDT" are the same thing. Build from UserTypes where a shape repeats (every pump, every valve). |
| **Commissioning (record)** | Driving each point and reading it back with quality + timestamp, and the document that captures that evidence: `Documentation/Commissioning-Record.md`. | The verifiable proof the system works: per-point write→read-back evidence + a named human sign-off. An automated "PASS" is evidence, **not** acceptance. |
| **Deliverable** | What the customer receives: the running Solution plus its signed Commissioning Record, and the handover Documentation. | A working, verified result, not a description of one. |
| **Handover** | The point at which the verified Solution and the signed Commissioning Record pass to the customer; the as-built / O&M docs in `Documentation/` support it. | End state of the work flow; the docs stay maintainable for years after. |
| **Site / Skid / Line** | The physical scope a Project covers, a Site (a plant / facility), a Skid (a self-contained packaged unit), or a Line (a production line). One scope = one Project. | Sets the granularity of `Sites/<Name>/`. Stakes (downtime / safety), not tag count, set how much rigor a Project needs: a small skid can be safety-critical. |
| **Decision (record)** | A short note under a Project's `Decisions/` capturing *how & why* something was configured, alternatives rejected, gotchas. | Companion to the ChangeLog: the **ChangeLog says what changed and when; a Decision says why.** A decision that helps *other* projects is promoted to `KnowledgeBase/`. |
| **Template (site skeleton)** | The blank starting point for a new Project: the `Templates/SiteProject/` folder of `*.template.md` files that `new-project-bootstrap` copies to seed a Project's `Specifications/`, `Documentation/`, `Tests/`, and `ChangeLogs/`. | The workspace's seed blanks, **document** scaffolds, never a `.dbsln`. Disambiguate from the **product's** Template (the New-Solution wizard's starter *solutions*): when both could be meant, say "site template" / "the SiteProject skeleton" for this one, and "New-Solution template" for the product's. |
